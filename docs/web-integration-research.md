# Исследование бесплатной веб-интеграции DeepSeek

Проверено 2 ноября 2026 года. Цель — нативный Compose-клиент для существующего бесплатного аккаунта. Developer API и замена нативного чата сайтом не входят в решение.

**Результат:** доступ к профилю, каталогу и истории через отдельный HTTP-клиент технически подтверждён. Записанная потоковая генерация разобрана и сверена с серверной историей. Полная Android-интеграция не реализована: допустимость использования приватного протокола по условиям сервиса не подтверждена; перенос авторизации из Android WebView и штатное выполнение PoW на Android не проверены. `DeepSeekWebProvider` остаётся отключённым. Этот отчёт не означает появления реальных ответов в APK.

## Доказательства и границы проверки

Локально разобраны три предоставленных HAR от 02.11.2026, 17:36:03, 17:38:14 и 17:40:00. HAR, учётные данные, идентификаторы аккаунта/диалогов и тексты сообщений не добавлены в проект. Диагностика выводила только структуру, статусы и результаты сравнения. Данные отправлялись только исходному HTTPS-сервису `chat.deepseek.com`, без перехода по редиректам и с обычной проверкой TLS.

Выполнены отдельным Python HTTPS-клиентом с авторизацией из предоставленной записи:

| Проверка | Результат |
| --- | --- |
| `GET /api/v0/users/current`, только Bearer | HTTP 200, `code = 0`, `biz_code = 0` |
| Тот же запрос с Bearer и cookies | HTTP 200, `code = 0`, `biz_code = 0` |
| `GET /api/v0/chat_session/fetch_page?lte_cursor.pinned=false` | Успешно, поля `chat_sessions`, `has_more` |
| `GET /api/v0/chat/history_messages?chat_session_id=…` | Успешно, сообщения находятся в `chat_messages` |
| `POST /api/v0/chat/create_pow_challenge` для `/api/v0/chat/completion` | Успешно получена новая задача; решение не вычислялось и не отправлялось |

Проверки каталога, истории и получения challenge тоже прошли без cookies. Это доказывает достаточность Bearer для этих проверенных запросов в момент исследования. Для генерации такой вывод не сделан: все пять записанных completion-запросов содержат Bearer, cookies и `x-ds-pow-response`. Переносимую сессию из самого Android WebView ещё необходимо проверить отдельно; здесь использовалась существующая браузерная сессия из HAR.

Во время исследования не повторялись записанные отправки сообщений, создание/удаление чатов и OAuth-запросы. Выполнены запросы чтения и получение временной PoW-задачи. CAPTCHA, WAF и PoW не обходились; режим TLS не ослаблялся.

## Наблюдаемый контракт

| Операция | Подтверждённая форма |
| --- | --- |
| Профиль | `GET /api/v0/users/current`; результат в `data.biz_data` |
| Каталог | `GET /api/v0/chat_session/fetch_page`; `data.biz_data.chat_sessions` и `has_more` |
| История | `GET /api/v0/chat/history_messages?chat_session_id=…`; `data.biz_data.chat_messages`, `chat_session`, `cache_control`, `cache_reset_at` |
| Создание, запись HAR | `POST /api/v0/chat_session/create`, JSON `{}`; `data.biz_data.chat_session` |
| Удаление, запись HAR | `POST /api/v0/chat_session/delete`, массив `chat_session_ids` |
| Авторизация, запись HAR | `POST /api/v0/users/oauth/get_token`, поля `nonce`, `provider`; ответ содержит token и user. Это внутренний обмен официального сайта, не публичный OAuth-контракт для SnowSeek |
| Генерация, запись HAR | `POST /api/v0/chat/completion`, ответ `text/event-stream` |

В JSON нужно проверять HTTP-статус, `code` и `data.biz_code`. Получен реальный ответ истории с HTTP 200 и `biz_code = 1`; считать его успешной загрузкой нельзя. Причина недоступности этого диалога не установлена.

Тело completion в HAR: `chat_session_id`, `parent_message_id`, `model_type`, `prompt`, `ref_file_ids`, `thinking_enabled`, `search_enabled`, `action`, `preempt`. `parent_message_id` и `model_type` могут быть `null`. Наличие этих полей в записи не устанавливает стабильный публичный контракт.

У completion также наблюдаются `x-hif-dliq` и `x-hif-leim`. Их назначение и обязательность не установлены. Значения не переносились в код и не использовались для имитации браузера.

## SSE: результат воспроизведения

Пять записанных HTTP 200-потоков содержат `ready`, `update_session`, обычные сообщения, иногда `title`, затем `close`.

- `ready` задаёт `request_message_id` и `response_message_id`.
- Начальный снимок находится в `v.response`, содержимое — в `fragments`.
- Канал `THINK` относится к размышлениям, `RESPONSE` — к ответу. Подмена одного другим не требуется.
- Для обычных patch-сообщений пропущенные `p` и `o` наследуются от предыдущего patch. В том числе встречается явный `p = response/fragments/-1/content` без `o` после APPEND.
- `APPEND` дополняет строку или массив; `SET` заменяет значение. Вложенные пути внутри `BATCH` относительны базовому пути; проверенный отсутствующий оператор дочернего patch — SET.
- Сам обрыв HTTP-соединения не подтверждает завершение генерации: нужны состояние ответа и завершающее событие.

Локальное воспроизведение восстановило все пять потоков до `close`. Для четырёх удалось найти сообщение по `response_message_id` в текущей истории: итоговые THINK и RESPONSE совпали **побуквенно**. Для одного диалога сервер вернул `biz_code = 1`, поэтому сравнение с историей не выполнено. Новые генерации этим тестом не запускались.

Это уточнение важно при переносе открытой реализации: её `updates.ts` не обрабатывает явно заданный content-путь с отсутствующим `o`, хотя такие кадры есть в предоставленных HAR.

## PoW и Android

Записанная цепочка — получение challenge, выполнение проверки официальным клиентом, передача `x-ds-pow-response`, затем SSE. Открытая реализация исполняет официальный Web Worker и передаёт результат проверки. Штатное выполнение проверки не следует смешивать с её обходом.

Для SnowSeek нельзя пропускать проверку, подделывать proof, повторно использовать истёкший proof или встраивать обход CAPTCHA/WAF. Возможный технический вариант требует отдельной проверки штатного worker в авторизованном Android WebView и привязки результата к конкретной задаче. Наличие скачиваемого worker не доказывает его работу на Android. В этом исследовании worker не исполнялся, generation-запросы не выполнялись.

Android-устройство/эмулятор не подключены. Не проверены захват сессии по явному действию пользователя внутри WebView, её защищённое хранение, срок действия, повторный вход, полный цикл отправки/остановки и восстановление после потери SSE. Сохранение ответа на устройстве не заменяет проверку серверного состояния генерации.

## Ограничение по условиям сервиса

Официальные [DeepSeek Terms of Use](https://cdn.deepseek.com/policies/en-US/deepseek-terms-of-use.html), обновление 27.03.2026, п. 3.5(3), ограничивают reverse engineering и захват/копирование содержимого сервиса, в том числе автоматическими средствами. Пункт 3.1 резервирует не предоставленные явно права. Публичного разрешения на исследуемый способ доступа стороннего нативного клиента не найдено.

**Оценка соответствия ТЗ:** доказательств технической невозможности доступа к данным нет; профиль и история работают. При этом условие проекта «реализовать интеграцию только если она допустима по условиям сервиса» пока не выполнено. Поэтому эксперимент с HAR не включён как работающий провайдер в распространяемый APK. Для включения нужна подтверждённая допустимость такого использования со стороны DeepSeek, затем проверка полной Android-цепочки. Это ограничение нельзя устранить выдачей демонстрационного ответа за настоящий.

MIT-лицензия стороннего адаптера разрешает использование его кода с сохранением уведомлений, но не предоставляет разрешения DeepSeek на доступ к сервису. Сторонние исходники не копировались в SnowSeek и не запускались с пользовательскими данными.
